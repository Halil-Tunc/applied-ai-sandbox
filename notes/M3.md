## Step 4 — good-context plan

Claude proposed adding a login flow with a clearer scope than the bad-context run. Its plan included:

### Context
The app is a minimal Flask note-taking app with an in-memory `app.notes` list and no current user system. The goal is to add register, login, and logout while keeping existing Task 1 tests passing.

### Key decisions
- Keep Task 1 tests passing by not forcing login on `/notes/new`.
- Use Flask-Login for session management.
- Use `werkzeug.security` for password hashing.
- Store users in a new SQLite `users` table.
- Do not add password reset, email verification, social login, or remember-me cookies.
- Do not edit the tests.
- Keep notes in the existing in-memory list, but associate notes with `user_id`.

### Files Claude expected to change
- `requirements.txt` to add Flask-Login.
- `app.py` for routes, login manager setup, database helpers, and auth logic.
- `templates/login.html` for the login form.
- `templates/register.html` for the registration form.
- `templates/home.html` for logged-in navigation and logout link.

### Route plan
- `/register`: render a registration form and create a user with a hashed password.
- `/login`: render a login form, check the password hash, and log the user in.
- `/logout`: log the user out and redirect to `/login`.
- `/`: require login and show only the current user’s notes.
- `/notes/new`: keep the existing Task 1 behavior, but attach `user_id` when a logged-in user creates a note.

### Verification plan
- Run `pytest tests/test_task_01.py -v`.
- Manually test register, login, logout, note creation, and two users seeing separate notes.
